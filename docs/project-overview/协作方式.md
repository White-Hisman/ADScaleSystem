

### 3.1 协作方式

项目使用 Git 进行版本管理，远程仓库托管在 GitHub、GitLab、Gitee 或学校指定平台。成员在自己的开发分支上编写代码，通过 **Pull Request（PR）** 或 **Merge Request（MR）** 提交评审，审核通过后合并到 `main`。

建议分支结构：

| 分支   | 用途                                             |
| ------ | ------------------------------------------------ |
| `main` | 稳定主分支，只合并已评审、可构建的代码。         |
| `A`    | 系统框架、主窗口、导航、医院管理、随访管理。     |
| `B`    | Qt 界面、患者管理、通用表单控件和输入校验。      |
| `C`    | SQLite、数据访问、查询统计、导入导出、备份恢复。 |
| `D`    | 临床资料、SCD、HAMD、HAMA、GDS 等量表。          |
| `E`    | 神经心理、功能、睡眠量表及计时、评分录入。       |

如需多人同时开发同一模块，从对应成员分支创建短期功能分支，例如 `feature/patient-search`。功能分支完成后先合回所属成员分支，再通过 PR/MR 合入 `main`。

### 3.2 第一次获取仓库

#### 第一步：安装并配置 Git

在终端或 Git Bash 中检查 Git 是否已安装：

```bash
git --version
```

配置提交者姓名和邮箱。此信息会出现在 Git 提交记录中：

```bash
git config --global user.name "你的姓名"
git config --global user.email "你的邮箱"
```

检查配置：

```bash
git config --global --list
```

#### 第二步：从代码托管平台获取仓库地址

在项目仓库页面点击“克隆”或“Code”，复制 HTTPS 或 SSH 地址。例如：

```text
https://example.com/group/project.git
```

如果使用 HTTPS，首次推送时可能需要使用平台提供的访问令牌；如果使用 SSH，需要先在托管平台配置 SSH 公钥。以项目平台的认证要求为准。

#### 第三步：克隆仓库到本地

在终端进入准备存放代码的目录，然后执行：

```bash
git clone https://example.com/group/project.git
cd project
```

查看本地分支和远程仓库：

```bash
git branch
git remote -v
```

克隆完成后，用 Qt Creator 打开仓库目录中的 `CMakeLists.txt`，选择可用的 Qt Kit，再构建和运行项目。不要把项目复制到 Qt 安装目录中。

#### 第四步：开始开发前同步代码

```bash
git switch main
git pull origin main
```

如果你的 Git 版本不支持 `git switch`，可使用：

```bash
git checkout main
```

---

### 3.3 首次创建并推送成员分支

每位成员第一次开发时，从最新的 `main` 创建自己的分支：

```bash
git switch main
git pull origin main
git switch -c A
git push -u origin A
```

其他成员将 `A` 替换为自己的分支名，例如：

```bash
git switch -c B
git push -u origin B
```

`-u` 用于设置本地分支和远程分支的跟踪关系。后续在该分支上可以直接使用 `git push` 和 `git pull`。

查看当前所在分支：

```bash
git branch --show-current
```

---

### 3.4 日常开发与提交

开始工作前，先切换到自己的分支并获取远程更新：

```bash
git switch B
git pull origin B
```

如果成员分支需要包含最新的主分支改动，可在确认工作区干净后同步：

```bash
git fetch origin
git merge origin/main
```

开发完成后检查改动：

```bash
git status
git diff
```

将需要提交的文件加入暂存区。推荐明确指定文件：

```bash
git add src/patient/PatientPage.cpp src/patient/PatientPage.h
```

确认暂存内容：

```bash
git diff --cached
```

提交代码：

```bash
git commit -m "feat: 添加患者详情页"
```

推送到远程分支：

```bash
git push
```

如果首次推送该分支：

```bash
git push -u origin B
```

#### 提交信息格式

使用简洁的类型前缀：

```text
feat: 添加患者详情页
fix: 修复条件题未按规则隐藏的问题
refactor: 调整量表记录保存接口
test: 增加随访状态测试
docs: 更新系统架构说明
build: 配置 Qt Widgets 与 CMake 工程
```

每个提交尽量围绕一个主题，避免把无关功能放在同一个提交里。

---

### 3.5 提交前检查

推送之前至少执行以下检查：

```bash
git status
git diff
```

确认：

- 当前在自己的开发分支，而不是 `main`。
- 提交内容只包含本次任务相关文件。
- Qt 项目能够构建，修改功能已进行相应测试。
- 没有提交数据库文件、构建目录、临时文件、访问令牌或真实患者信息。
- 新增或修改的量表字段符合已确认的数据字典和原始量表版本。

`.gitignore` 应排除本机构建输出和用户本地配置，例如：

```gitignore
build/
cmake-build-*/
*.user
*.sqlite
*.db
```

如项目需要提交虚构测试数据库，应使用明确的演示数据文件名，并先确认团队的仓库规则；真实患者数据不得进入 Git 仓库。

### 3.6 创建 PR / MR

代码推送后，在代码托管平台打开项目仓库：

1. 选择“新建 Pull Request”或“新建 Merge Request”。
2. 将目标分支设为 `main`。
3. 将来源分支设为自己的成员分支或功能分支。
4. 填写标题和说明。
5. 指定评审人。
6. 等待检查和评审完成后再合并。

PR 标题示例：

```text
feat: 完成患者管理页面
fix: 修复量表草稿恢复问题
```

PR 说明建议包含：

```text
改动内容：
- 增加患者列表和详情页面
- 接入患者查询接口

测试情况：
- Qt 工程构建通过
- 新增患者、编辑患者和查询流程已验证

注意事项：
- 需要数据库分支新增 patient 查询接口
```

PR/MR 应保持范围明确。若同时修改界面、数据库结构和多个量表，建议拆分成多个 PR，或在说明中列出依赖关系。

---

### 3.7 评审与合并

合并前由作者和评审人确认：

- 改动符合分工和已确认需求。
- 工程可构建，主要操作流程已测试。
- 数据库和公共接口变更已通知相关负责人。
- 量表字段、条件逻辑、填写者类型和评分规则经过负责人核对。
- 不含真实患者数据、密钥或本地环境文件。

建议评审分工：

| 改动内容                     | 建议评审人                  |
| ---------------------------- | --------------------------- |
| 主窗口、导航、跨模块接口     | A 和相关模块负责人          |
| 数据库、迁移、导出与合并格式 | C、A                        |
| 患者页面、通用表单控件       | B、A                        |
| 临床量表字段和条件逻辑       | D、A；涉及数据库时请 C 评审 |
| 神经心理量表、计时和评分规则 | E、A；涉及数据库时请 C 评审 |

评审通过后，在平台上合并 PR/MR。团队应选定一种合并方式并保持一致，例如 **Squash and merge**。合并后同步本地主分支：

```bash
git switch main
git pull origin main
```

---

### 3.8 合并主分支更新到开发分支

`main` 有新改动时，开发成员应及时同步到自己的分支。先确认当前没有未提交内容：

```bash
git status
```

同步远程分支并合并主分支：

```bash
git fetch origin
git switch B
git merge origin/main
```

解决冲突后，再提交合并结果并推送：

```bash
git add 冲突文件路径
git commit -m "merge: 同步 main 更新"
git push
```

如果冲突出现在 `main` 中，或涉及数据库结构、公共接口和量表字段，应先与相关负责人确认处理方案，不要直接选择覆盖一方。

---

### 3.9 冲突处理

Git 提示冲突时：

1. 查看冲突文件：

   ```bash
   git status
   ```

2. 打开冲突文件，查找以下标记：

   ```text
   <<<<<<<
   =======
   >>>>>>>
   ```

3. 与相关模块负责人确认应保留、合并或重写的内容。
4. 删除冲突标记，并确认文件逻辑完整。
5. 构建并测试受影响模块。
6. 标记冲突已解决并提交：

   ```bash
   git add 冲突文件路径
   git commit -m "fix: 解决患者模块合并冲突"
   ```

不要用“保留全部当前版本”或“保留全部对方版本”代替代码审查。不得使用强制推送覆盖他人已提交的远程历史；确需改写历史时，先征得分支负责人同意。

### 3.10 常用命令速查

```bash
git status                         # 查看工作区状态
git branch --show-current          # 查看当前分支
git branch                         # 查看本地分支
git switch B                       # 切换到 B 分支
git pull origin B                  # 获取并合并 B 分支远程更新
git fetch origin                   # 获取远程分支信息，不自动合并
git diff                           # 查看未暂存改动
git diff --cached                  # 查看已暂存改动
git add 文件路径                   # 暂存指定文件
git commit -m "feat: 功能说明"     # 创建提交
git push                           # 推送当前跟踪分支
git log --oneline -10              # 查看最近提交记录
```

**基本工作循环：**

```text
克隆仓库
→ 切换到个人分支
→ 拉取最新代码
→ 修改和测试
→ git add
→ git commit
→ git push
→ 创建 PR/MR
→ 评审通过后合并到 main
→ 本地同步 main
```

### 3.11 项目协作约定

- 不直接在 `main` 上进行功能开发。
- 不提交真实患者资料、数据库备份和个人配置。
- 数据库结构、公共接口和数据字典改动必须提前告知相关成员。
- 每位成员对自己负责模块的改动进行自测，并在 PR 中说明测试结果。
- A 负责主分支集成和整体规范；模块负责人负责确认本模块的功能与数据正确性。
- 合并后及时同步主分支，保持各成员分支与集成代码基本一致。
